# ADR-0008：分片分阶段引入，阶段一/二保持单库

- 状态：Accepted
- 日期：2026-11-14
- 相关：`database/partitioning/`、`performance-design.md`、ADR-0003

## 背景

`README.txt` 第七节明确「初期不建议一次性引入 Flink、Spark、分布式数据库和多活架构」。
需要明确分片何时引入、以及引入后对一致性边界的影响。

## 决策

- 阶段一/二 `ShardRouter(shardCount=1)`，所有账户同分片，`ShardAwarePosting.sameShard` 恒真。
- 阶段三先做**分区与冷热分离**（`ledger_entry_archive`），再评估分库分表。
- 分片键按 `account_id` 稳定取模；跨分片交易必须显式识别，且**不能**继续套用 ADR-0003 的单库本地事务边界。
- 跨分片一致性协议（Saga/TCC/对账补偿）作为阶段五专题重新论证，本阶段不预设结论。

## 备选方案

| 方案 | 否决原因 |
| --- | --- |
| 一开始就分 16 库 | 正确性基线无法证明，且无法衡量每次架构升级收益 |
| 按时间分片 | 同一账户交易散落多片，余额约束难以保证 |
| 用分布式数据库屏蔽分片 | 阶段一引入过早，故障模式与调优复杂度过高 |

## 后果

**正面**：单库阶段可清楚衡量每次升级收益；分片路由提前存在，切换时业务代码改动小。

**负面**：分片后必须重新设计跨分片转账一致性；`I-2` 校验需按分片分别执行再汇总。
