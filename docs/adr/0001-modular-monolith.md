# ADR-0001：阶段一采用模块化单体

- 状态：Accepted
- 日期：2026-11-14
- 相关：`architecture.md`、`README.txt` 第九节

## 背景

`README.txt` 第二节给出了十余个微服务 + 引擎 + 基础设施的完整目录，但第九节明确「阶段一先构建单体模块化系统，证明资金正确性」。需要在「一次性铺开微服务」与「先建正确性基线」之间做取舍。

金融核心的首要风险是资金正确性；服务拆分会立即引入跨服务事务、网络超时不确定、消息重复等问题，使「不重复扣款、不超扣、不平衡分录」这类不变量难以证明。

## 决策

阶段一交付 **一个可部署单元（Modular Monolith）+ 一个关系数据库（默认本机 MySQL 8，可切换 PostgreSQL）+ 一个本地事务边界**；内部按未来服务边界强隔离模块（transaction / account / ledger / idempotency / outbox），依赖方向单向向下，用 ArchUnit 在 CI 强制校验。

`posting-engine` 作为 ledger 模块内的 Java 库，不独立部署。

## 备选方案

| 方案 | 优点 | 否决原因 |
| --- | --- | --- |
| 直接微服务化 | 贴近最终目录、看似「完整」 | 跨服务一致性无法在单事务内证明，正确性基线不稳 |
| 纯单体无模块边界 | 最简单 | 阶段二拆分时边界不清，重构成本大 |
| 引入分布式事务框架（XA/TCC/Seata） | 可跨服务 | 复杂度与故障模式远超阶段一需求，且资金正确性不因此更强 |

## 后果

**正面**
- 余额、分录、幂等记录、Outbox 在同一 COMMIT 内，不变量可由数据库约束 + 本地事务直接保证。
- 崩溃恢复简单：未提交事务 DB 自动回滚。
- 阶段二拆分时模块边界已就位，只需把进程内调用替换为 RPC + Outbox 投递。

**负面 / 代价**
- 阶段一无法展示多 AZ、服务治理等能力（本就是阶段四内容）。
- 单库成为吞吐上限，500 TPS 目标足够，阶段三再分片。
- 需靠纪律（ArchUnit + Code Review）维持模块边界，否则退化为大泥球。

## 验证

`test-strategy.md` 的 TC-1/TC-4/TC-8 与 `consistency.md` 的 I-1~I-6 校验 SQL，在拆分前后必须保持同样的通过标准。
