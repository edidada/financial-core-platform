# ADR-0009：热点账户采用缓冲净额折叠，但落库仍走单事务边界

- 状态：Accepted（专题，阶段五）
- 日期：2026-11-14
- 相关：`11-incident-reviews/expert-topic-hotspot-posting.md`、ADR-0003、ADR-0004

## 背景

热点账户逐笔 `SELECT FOR UPDATE + UPDATE` 导致锁竞争、吞吐退化（README 6.1）。
需要优化但不能牺牲资金正确性。

## 决策

- 新增 `engines/hotspot-accounting-engine`：`HotspotBuffer` 在时间窗内做**准入判定 + 净额折叠**（纯内存计算）。
- 准入：`bufferedDebit + 本笔借方 <= 可用余额`，锁内判定防超扣（I-4）。
- 折叠：按 `(accountId, direction)` 汇总，保持 `ΣD=ΣC`（I-1）与总量不变（I-2）。
- **落库仍由 `JdbcPostingEngine` 在调用方本地事务内完成**：余额、分录、Outbox 一次 COMMIT（ADR-0003）。
- 只在 `drain()` 落库成功后才向客户端确认；原凭证与冲正语义不变（ADR-0004）。
- 仅对识别出的热点账户启用；普通账户继续逐笔入账。

## 备选方案

| 方案 | 否决原因 |
| --- | --- |
| 异步队列串行扣款 | 若先确认后入账，崩溃会丢账；且账务恢复复杂 |
| Redis 预扣余额 | 违反「Redis 不参与资金正确性」第一原则 |
| 放宽隔离级别换吞吐 | 可能超扣，硬约束不允许 |
| 去掉行锁只靠条件 UPDATE | 热点下大量事务冲突重试，吞吐未必改善且延迟不可控 |

## 后果

**正面**：热点单账户落库次数由 `n` 降为约 2，锁竞争显著减少；不变量有属性测试证明。

**负面**：引入窗口内可见性延迟；进程崩溃会丢失未落库缓冲（靠短窗口 + 状态机 + Outbox 恢复）；
长窗口放大在途交易规模；查询 API 需明确「已提交余额」口径。
