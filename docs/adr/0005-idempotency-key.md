# ADR-0005：以幂等键 + 唯一约束 + 结果快照实现端到端幂等

- 状态：Accepted
- 日期：2026-11-14
- 相关：`transaction-design.md` 第四节、`consistency.md` 第五节、Stripe 幂等实践

## 背景

网络超时、客户端重试、消息重复投递是常态。`README.txt` 第六节要求「100 万次重复请求，同一业务仅生效一次」；4.3 强调「请求超时 ≠ 业务失败」。若缺乏幂等，重试必然导致重复扣款（违反硬约束「重复请求导致重复扣款 = 0」）。

## 决策

**幂等三要素，缺一不可：**

1. **唯一约束（DB）**：`idempotency_record(tenant_id, idempotency_key)` 主键唯一；`journal.biz_id` 唯一。
2. **状态机（应用）**：`UNKNOWN` 状态不得直接重试业务，必须先查询账务事实（见 `transaction-design.md` 第五节）。
3. **结果快照（响应）**：首次成功时把状态码 + 响应体存入 `idempotency_record`，重复请求直接返回快照，不重新执行业务。

处理流程：

```
请求(带 Idempotency-Key)
  -> 查幂等记录
     ├ 命中且成功          -> 返回快照 (200, 原结果)
     ├ 命中且参数 hash 不同 -> 409 CONFLICT
     ├ 命中且处理中         -> 202 + 原交易号 (客户端轮询)
     └ 未命中              -> 同事务插入记录 -> 执行业务 -> COMMIT -> 写回结果
```

- 幂等记录与交易/分录/余额/Outbox **同一事务**写入（ADR-0003），避免「记录了却没入账」。
- 请求参数做 `request_hash`，防止同一键被复用于不同请求。
- 阶段二消费 Kafka 时，消费侧以 `biz_id` 去重，不依赖「消息恰好一次」。

## 备选方案

| 方案 | 否决原因 |
| --- | --- |
| 仅靠前端去重 / Token | 客户端不可信，重试与超时无法覆盖 |
| 仅靠 DB 唯一约束、不存结果 | 重复请求会报错而非返回一致结果，客户端无法收敛 |
| 靠「恰好一次」消息投递 | 分布式系统不存在端到端恰好一次，必须消费侧幂等 |
| 超时即重试业务 | 会把 UNKNOWN 误判为 FAILED，导致重复入账 |

## 后果

**正面**
- 满足硬约束「重复请求导致重复扣款 = 0」。
- 客户端可安全重试，超时后有明确的查询与收敛路径。
- 阶段二消息重复投递同样被 `biz_id` 挡住。

**负面 / 代价**
- 幂等记录表持续增长，需定义保留期与归档策略（阶段三）。
- 需要客户端配合生成并复用稳定的幂等键；API 文档必须强制该 Header。
- 「处理中」返回 202 要求客户端实现轮询，交互略复杂。

## 验证

`test-strategy.md` TC-4：100 万次重复请求，成功入账恰好 1 次；TC-5 超时/崩溃恢复不产生第二笔账务。
