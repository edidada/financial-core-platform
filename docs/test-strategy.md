# 阶段一测试策略与验收（Test Plan）

> 状态：设计中 · 对应 README 第六节压测矩阵（阶段一部分）· 依赖 `consistency.md`

## 一、目标

阶段一测试的唯一核心命题：**在并发、重试、超时、崩溃条件下，资金不变量 I-1~I-6 恒成立**。压测只用于建立基线，不以 TPS 数字本身为目标。

## 二、测试金字塔

| 层次 | 工具 | 覆盖 | 占比目标 |
| --- | --- | --- | --- |
| 单元测试 | JUnit 5 | 状态机迁移、借贷平衡、金额运算、幂等判定 | 高 |
| 集成测试 | Testcontainers + PostgreSQL | 事务边界、DDL 约束、Flyway 迁移 | 中 |
| 并发测试 | JUnit + 线程池 / Gatling | 并发扣款、热点账户、死锁 | 中 |
| 幂等/重试测试 | 自研压测驱动 | 百万次重复请求 | 中 |
| 属性测试 | jqwik | 随机交易序列下的不变量 | 低 |
| 性能基线 | Gatling + JMH | 500 TPS / P99 / GC / SQL 计划 | 低（阶段一） |

## 四、并发扣款测试设计（TC-1 细化）

```
准备：account_balance(10001) = 10000 分
并发：1000 线程同时提交「扣 8000 分」交易，各自带幂等键
断言：
  成功笔数 == 1
  最终 available_balance == 2000
  ledger_entry 中该账户只有 1 条扣款分录
  journal 数与成功笔数一致
  I-1~I-6 校验 SQL 全部 0 行
重复：不同隔离级别、不同连接池大小、有无 FOR UPDATE 各跑一轮
```

## 五、不变量检查工具

提供 `ledger-invariant-checker`（阶段一交付 FR-9）：

```
输入：数据库连接 + 时间范围
输出：I-1~I-6 六项检查报告（异常行明细 + 汇总）
用途：CI 门禁、每次压测后必跑、故障恢复后复核
```

校验 SQL 见 `consistency.md` 第二节。该工具是「成果 A：资金一致性」的可重复验证物（README 第十节）。

## 六、性能基线记录要求

每次测试必须记录（README 第六节）：CPU 型号与核数、内存、磁盘、网络、JVM 参数、数据库版本、数据量、并发数、负载模型、错误率、P50/P95/P99/P99.9、GC、数据库等待事件。

| 指标 | 阶段一目标 |
| --- | --- |
| 交易 API 吞吐 | 500 TPS |
| 账务入账吞吐 | 300 TPS |
| 核心交易 P99 | < 200 ms |
| 查询 P99 | < 100 ms |

阶段一 **不**追求 5,000 TPS / 亿级数据，那些是阶段三目标，且必须结合硬件与数据分布调整，不能预设可达。

## 七、CI 门禁

- 全量单测 + 集成测试（Testcontainers 起空库跑 Flyway 全量迁移）。
- ArchUnit 校验模块依赖方向，防止账务表被越权访问。
- TC-1 / TC-4 / TC-8 作为 PR 必跑用例。
- 不变量检查工具输出非 0 行异常 → 直接失败。
